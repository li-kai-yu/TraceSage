# 01 架构与限界上下文

## 1. 系统定位

TraceSage 解决两个问题：

1. **链路可观测**：业务系统一次请求经过了哪些服务、哪些方法、耗时多少、在哪里失败。
2. **故障可诊断**：链路出现异常时，自动结合历史故障案例（RAG）推断根因并生成报告。

## 2. 限界上下文（Bounded Context）

按 DDD 划分限界上下文，每个上下文拥有自己的领域模型、自己的数据表、自己的语言。
**禁止跨上下文直接引用对方的实体类或表**，跨上下文只能通过接口（Feign / MQ 事件）交互。

| 上下文 | 职责 | 核心聚合 | 所属服务 |
| --- | --- | --- | --- |
| **IAM**（身份与访问） | 用户、角色、权限、登录认证、令牌签发与注销 | User、Role、Permission | tracesage-system |
| **Tracing**（链路追踪） | 埋点数据接收、清洗、存储、链路检索与拓扑还原 | Trace、Span | tracesage-system |
| **Insight**（故障洞察） | 故障案例知识库、RAG 召回、根因推理、报告生成 | FaultCase、AnalysisReport | tracesage-insight |

> 说明：为控制模块数量，IAM 与 Tracing 合并部署在 tracesage-system 中，
> 但**代码上仍按上下文分包隔离**，便于后续独立拆分。

## 3. 微服务模块划分

| 服务 | 端口 | 依赖 | 说明 |
| --- | --- | --- | --- |
| tracesage-gateway | 8080 | Redis | 统一入口。路由转发、JWT 鉴权、限流。响应式模型，**禁止依赖 spring-boot-starter-web** |
| tracesage-system | 8081 | MySQL、Redis、RabbitMQ、ES | IAM + Tracing 两个上下文的宿主 |
| tracesage-insight | 8082 | MySQL、ES、LLM | RAG 知识库 + Agent 根因分析 |
| tracesage-trace-sdk | - | RabbitMQ / HTTP | 被业务方引入的埋点 SDK，不部署 |

## 4. 调用与数据流

```
业务应用 ──引入──> tracesage-trace-sdk
                        │ 1. 生成 TraceId / SpanId，采集方法耗时
                        ▼
                  RabbitMQ (exchange: tracesage.trace.exchange)
                        │ 2. 异步投递链路数据
                        ▼
              tracesage-system / infrastructure.mq 消费者
                        │ 3. 数据清洗（截断、脱敏、补全） → 写入 ES 索引 trace-span
                        ▼
   ┌────────────────────┴────────────────────┐
   │ 4a. 链路查询接口                         │ 4b. 异常链路触发分析
   ▼                                          ▼
tracesage-system 查询 ES              tracesage-insight
   ▲                                          │ 5. RAG 召回历史故障案例
   │                                          │ 6. Agent 推理根因
   └──────────── 前端 / 网关 ◄────────────────┘ 7. 生成报告并落库
```

## 5. 服务间交互约束

| 场景 | 方式 | 约束 |
| --- | --- | --- |
| 前端 → 网关 → 服务 | HTTP | 网关负责鉴权，服务只信任网关透传的用户信息 |
| 服务 → 服务 同步调用 | OpenFeign | 必须定义独立的 `api` 接口，禁止直接依赖对方的 `application`/`infrastructure` 包 |
| 服务 → 服务 异步通知 | RabbitMQ | 事件类定义在发起方 `domain.event`，消费者做防腐转换 |
| 链路数据上报 | RabbitMQ | 使用独立交换机/队列，与业务消息隔离 |

## 6. 分层依赖规则（强制）

```
interfaces ──► application ──► domain ◄── infrastructure
                                   ▲
                                   └── 仓储接口 / 网关接口由 domain 定义、infrastructure 实现
```

- 上层可以依赖下层，**下层绝不能依赖上层**。
- `domain` 不依赖任何其他层，也不依赖 Spring、MyBatis、ES 等框架。
- 依赖倒置：`domain` 定义 `repository` / `gateway` 接口，`infrastructure` 提供实现。
- 越层调用（Controller 直接调 Repository、Controller 直接调 Mapper）**一律禁止**。

## 7. 分阶段开发顺序

| 阶段 | 内容 | 涉及模块 |
| --- | --- | --- |
| 1 | DDD 骨架、数据库、登录 RBAC | common-*、gateway、system(IAM) |
| 2 | 手写简易 Trace 埋点 SDK，跑通链路采集 | trace-sdk |
| 3 | RabbitMQ 消费链路数据、数据清洗 | system(Tracing) + common-mq |
| 4 | ES 存储链路、实现链路查询接口 | system(Tracing) + common-es |
| 5 | 构建 RAG 知识库，存储历史故障案例 | insight |
| 6 | LangChain4j Agent 集成，根因分析、生成报告 | insight |
| 7 | 全局异常、AOP、Knife4j、Docker 打包 | common-web + 各服务 |
